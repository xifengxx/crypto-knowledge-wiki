# RGB 协议

## 基本信息
- 类型: 比特币智能合约协议 / 客户端验证协议
- 提出时间: 2016 年，由 Bitcoin Core 开发者 Peter Todd 提出核心概念（客户端验证 + 一次性密封）
- 维护组织: LNP/BP 标准协会（Lightning Network Protocol / Bitcoin Protocol），非营利组织，覆盖比特币协议、闪电网络协议和 RGB 等智能合约标准
- 定位: 用于比特币和闪电网络的可扩展和保密智能合约协议套件，可在 UTXO 上运行复杂智能合约

## 核心机制

### 一次性密封（Single-use-seals）
将比特币 UTXO 作为"密封条"使用：创建 UTXO 时密封条锁上，花费 UTXO 时密封条打开。根据比特币共识规则，一个 UTXO 只能被花费一次，这一特性被 RGB 用来防止双重支付。与以太坊的账户模型不同，比特币的 UTXO 天然适合作为一次性密封的载体。

### 客户端验证 + 确定性比特币承诺
RGB 不要求全节点验证（不同于以太坊的全局验证），而是采用客户端验证（Client-side Validation）：只有交易相关方需要验证状态转换。RGB 将状态转换承诺（Commitment）嵌入特定的比特币交易中，利用比特币主网防止双花。承诺通过密码哈希函数转化为简短的确定性比特币承诺，借助 OpenTimeStamps 等协议实现"出版证明"（Proof-of-Publication）。

### 闪电网络兼容性
RGB 的状态转换承诺到比特币交易后，交易无需立即在链上结算——它可以成为闪电网络支付通道的一部分，借用闪电网络的安全性实现数字资产的快速流通。

### RGB v0.10 更新
在灵活性和安全性方面进行了重大升级，旨在降低开发者学习门槛并扩展功能范围。

## RGB vs Ordinals 五维对比

根据 Kernel Ventures 的分析，RGB 与 Ordinals 在五个维度上各有优劣：

| 维度 | Ordinals 优势? | 说明 |
|------|:---:|------|
| **安全性** | Ordinals | Ordinals 每笔交易/状态转移均通过链上 UTXO 花费实现；RGB 大量数据存储于本地缓存或云服务器，存在中心化丢失风险 |
| **验证速度** | Ordinals | RGB 客户端验证需从头追溯每笔资产的完整转移历史，验证速度远慢于链上直接查询 |
| **隐私性** | RGB | RGB 资产转移和验证均在链下发送者-接收者间特有信道进行，盲化 UTXO 使发送者也无法追溯去向；Ordinals 全部链上公开可查 |
| **交易费用** | RGB | RGB 中间任意多笔交易几乎 0 费用，最终仅需 1 个 UTXO 链上确认；Ordinals 每笔转账都需上链且只能一对一转账 |
| **可扩展性** | RGB | RGB 交易验证和数据存储不在主链进行，每个节点仅保存相关数据；Ordinals 铭文数据全部上链 |

## 技术机制补充

### 盲化 UTXO（Blinded UTXO）
RGB Token 转移时，发送方无法获得接收 UTXO 的具体地址，只能得到 `Hash(接收UTXO地址 + 随机密码值)`。接收方后续使用时，需同时提供 UTXO 地址和密码值向下一接收者验证。此机制在保护隐私的同时不影响双花防护。

### 批量打包交易
RGB 支持在一个 Tapscript 脚本中指定多个接收者，通过分摊大幅降低每笔转账成本。Ordinals 默认输出 UTXO 接收者即为资产接收者，只能一对一转账。

## 为何进展缓慢
- 早期版本功能相对有限
- 开发者学习门槛高
- **客户端验证速度慢**：每验证一笔交易需从头追溯全部 RGB 资产转移历史，这是比开发者门槛更根本的技术瓶颈
- 智能合约之间无法直接交互（只能点对点转账）
- 自 2016 年提出以来，经过数年发展仍未能获得广泛关注和应用

## 竞争优势
- **隐私性极强**：只有交易双方知道合约内容，链上仅存储承诺哈希，第三方无法获知交易细节
- **可扩展性**：链下执行，不占用比特币主网区块空间
- **继承了比特币的安全性**：通过 UTXO 一次性密封机制防止双花
- **近乎零交易费用**：链下 RGB 通道或闪电网络转账几乎 0 费用，批量打包进一步降低成本

## 生态项目（2023 年中）
- **Infinitas** — 图灵完备的比特币应用生态系统，结合闪电网络与 RGB 协议优势；提出递归零知识证明方案压缩客户端验证体量，若有效实施将大幅提升验证速度
- **RGB Explorer** — 最早支持 RGB 资产查询及发送的浏览器，支持 RGB20/RGB21/RGB25 三种标准资产
- **Cosminmart** — 兼容 RGB 协议的比特币闪电网络，提供钱包、衍生品交易市场和早期项目发掘市场的一站式服务
- **DIBA** — 借助闪电网络和 RGB 打造比特币 NFT 市场，2023 年中仍在测试网运行
- **Tether (USDT)** — 2023 年宣布将比特币二层网络上 USDT 合约部署从 OmniLayer 迁移至 RGB，被视为 Crypto 巨头认可 RGB 的信号

## 竞争 / 替代方案
- **BitVM** — 通过 Taproot 地址矩阵实现图灵完备虚拟机，基于欺诈证明，但工程实现极其困难
- **Ordinals/BRC-20** — 更简单粗暴的资产发行方式，虽然中心化风险更高但已经获得市场验证（BRC-20 市值 $6.4 亿，2023.12）
- **Atomicals/ARC-20** — 基于 UTXO 的资产发行，不依赖第三方排序器

## RGB++ 协议（2024）

RGB++ 是 RGB 协议的重要演进方案，由 Nervos/CKB 团队在 2024 年初提出。核心思路是将原始 RGB 的"客户端验证"替换为"第三方去中心化平台验证"，通过**同构绑定（Isomorphic Binding）**将 RGB 资产映射到支持拓展型 UTXO 的公链上。

### 同构绑定机制
将 CKB、Cardano、Fuel 等 UTXO 公链的拓展型 UTXO 作为 RGB 资产数据的"容器"，把 RGB 资产参数写入容器中并在链上直接展示。当 RGB 资产交易发生时，对应的资产容器也呈现相似特征——"实体和影子的关系"。例如：Alice 在比特币链上花费 UTXO A 并发布 Commitment 声明转移 30 枚 Token 给 Bob，同时在 CKB 链上将承载 100 枚 Token 的 UTXO 容器消费掉，生成两个新容器（30 枚给 Bob + 70 枚 Alice 控制）。

### 关键变化
| 维度 | 原始 RGB | RGB++ |
|------|---------|-------|
| **验证方式** | 客户端验证（用户自行验证） | 平台共识验证（CKB/Cardano 节点验证） |
| **数据存储** | 本地数据孤岛 | 链上全局可见 |
| **转账模式** | 交互式（≥3 次消息传递） | 非交互式（与传统链上转账一致） |
| **隐私性** | 极强（只有交易双方知道） | 较弱（链上公开，可借助 ZK 改善） |
| **DeFi 兼容** | 困难（无全局账本） | 良好（全局可验证状态） |
| **信任假设** | Trustless（无需信任任何第三方） | 需乐观信任 CKB/Cardano 共识 |

### 交易折叠
RGB++ 支持"交易折叠"：如果交易双方信任 CKB 等公链的安全性，可在多笔 RGB 转账后再汇总发送一个 Commitment 到比特币链上，降低使用成本。

### 兼容与切换
RGB++ 与原始 RGB 协议兼容——用户可根据需求在两种模式间切换。追求极致隐私和安全可用原始 RGB，追求便利性和 DeFi 可组合性可用 RGB++。

### 平台限制
同构绑定要求目标公链使用 UTXO 模型或类似状态存储方案，EVM 链（账户模型）不适合实现同构绑定。
