# zkVM

## 一句话定义
zkVM（零知识虚拟机）是一个通用虚拟机，能够为任意程序的正确执行生成零知识证明（SNARK），使不信任的验证方可以在不重新运行程序的情况下确认其执行结果。

## 核心原理
zkVM 通过以下机制实现通用程序执行的零知识证明：

1. **执行轨迹编码**：将虚拟机（如 RISC-V）的有效执行轨迹编码为约束系统（constraint system），涵盖寄存器和内存使用。
2. **PIOP（多项式交互式预言机证明）**：构建交互式证明框架，将约束满足转化为多项式陈述。
3. **PCS（多项式承诺方案）**：防止证明者在多项式求值上撒谎。
4. **SNARK 应用**：对约束满足性应用简洁的非交互式零知识证明。

zkVM 的核心理念是"民主化 SNARKs"——让任何开发者都能为其程序生成零知识证明，无需专门的 SNARK 专业知识。

## zkVM 与 zkEVM 的区别
- zkVM 是通用架构（通常基于 RISC-V 等通用指令集），可用于任何程序的证明
- zkEVM 是特定于以太坊的 zkVM，专门为证明 EVM（以太坊虚拟机）执行而设计
- zkEVM 本质上是 zkVM 的一个特例，但 zkVM 可服务于更广泛的场景

## 为什么重要
- ZK-Rollup 的核心技术组件：zkVM 使 L2 能够向 L1 证明批次交易的正确性，无需重新执行
- 跨链桥：使一条链能证明另一条链上发生的事件，无需信任中继器
- 隐私应用：允许在不透露输入数据的情况下证明正确执行（如隐私保护的身份验证、位置检查）
- 可验证计算：客户端可将计算外包给服务器，通过 zkVM 证明验证结果

## 关键挑战

### 安全性
zkVM 是极其复杂的软件项目，"仍然充斥着 bug"。a16z 研究合伙人 Justin Thaler 提出了安全性三阶段评估框架：
- **Stage 1**：形式化验证 PIOP 的健全性证明 + PCS 的 binding 性质 + Fiat-Shamir 转换下的安全性 + 约束系统=VM 语义的等价性
- **Stage 2**：形式化验证验证器实现与协议一致（确保可靠性——验证者不会被虚假陈述说服）
- **Stage 3**：形式化验证证明器实现正确生成证明（确保完备性）
- 预计时间线：Stage 1 ≥2 年，Stage 3 ≥4 年（来源：[[来源_2025-03_zkVM_安全_性能_a16z]]）

### 性能
当前证明开销极高 —— 比原生执行慢约 1,000,000 倍。性能三阶段评估框架：
- **Speed Stage 1**：单线程 ≤100,000x 慢于原生执行（≈每秒 30,000 RISC-V 周期 on 现代笔记本）
- **Speed Stage 2**：单线程 ≤10,000x 慢于原生执行
- **Speed Stage 3**：≤1,000x + 自动合成且形式化验证的预编译
- 预计时间线：Stage 1 可能在 2025-2026 年实现，Stage 2 需两年，Stage 3 需数年

### 内存
- **Memory Stage 1**：<2 GB 证明器内存，开启移动端/浏览器用例
- **Memory Stage 2**：<200 MB 证明器内存，使 HTTPS 证书证明等大规模应用可行

### 预编译依赖的两面性
预编译（pre-compiles）是针对特定函数（如 Keccak/SHA 哈希、椭圆曲线运算）定制的专用 SNARK 或约束系统。行业广泛依赖预编译来提升性能，但 a16z 研究指出其是"拐杖"：手工编写几乎肯定有 bug，且掩盖了底层证明系统的内在低效。

安全性和性能之间存在根本性张力："随着 zkVM 中发现更多漏洞，我预计一些漏洞只能通过大幅牺牲性能来修复。"在达到 Security Stage 2 之前，性能结果应被视为暂定性的。
