# zkVM 安全与性能之路：a16z crypto 的分阶段进度追踪框架

## 核心要点
- zkVM 面临两大核心挑战：安全性（代码极其复杂，仍有大量 bug）和性能（证明生成比原生执行慢数十万到数百万倍），Thaler 认为"我们距离实现最基本的目标还有数年之遥"
- 安全性分三阶段：Stage 1（形式化验证证明协议的健全性）、Stage 2（形式化验证验证器实现的正确性）、Stage 3（形式化验证证明器实现的正确性）。预计至少 2 年才能达到 Stage 1，4 年以上达到 Stage 3
- 性能分三阶段：Speed Stage 1（单线程证明 ≤100,000x 原生执行）、Stage 2（≤10,000x）、Stage 3（≤1,000x + 自动合成且形式化验证的预编译）。Thaler 认为当前行业宣传的"1000x 提升"是"对过去多糟糕的陈述，而非对现在多好的陈述"
- 预编译（pre-compiles）被行业广泛依赖，但 Thaler 认为这是"拐杖"：仍然太慢、安全风险高（手工编写几乎肯定有 bug）、开发者体验倒退到 1960 年代、混淆了性能基准评测
- 内存是移动端/浏览器用例的关键瓶颈：Memory Stage 1 要求 <2 GB 证明器内存，Stage 2 要求 <200 MB。手机是"我们与真实世界的持续连接"，实现低内存证明可开启隐私保护位置检查和可验证凭证等应用
- 安全性与性能相互依存："随着 zkVM 中发现更多漏洞，我预计一些漏洞只能通过大幅牺牲性能来修复"。在达到 Security Stage 2 之前，"性能结果应被视为暂定性的"

## 关键数据
- 当前证明开销：比原生执行慢约 1,000,000 倍（一百万倍）
- Speed Stage 1 目标：单线程 ≤100,000x 原生执行，即在现代笔记本上每秒约证明 30,000 个 RISC-V 周期
- Speed Stage 2 目标：单线程 ≤10,000x 原生执行
- Speed Stage 3 目标：≤1,000x + 自动合成且形式化验证的预编译
- 安全性时间线：预计没有任何 zkVM 能在 2 年内完全达到 Security Stage 1；达到 Stage 3 不早于 4 年
- 性能时间线：Speed Stage 1 有望在 2025 年内实现；Stage 2 未来两年可实现（但可能需要全新想法）；Stage 3 和 Memory Stage 2 需要数年
- 安全基准：100 bits 古典安全是"绝对最低底线"，标准实践要求 128 bits 及以上
- Memory Stage 1 要求：<2 GB 证明器内存（含零知识），即使证明超大语句（数万亿原生 CPU 周期）
- Memory Stage 2 要求：<200 MB 证明器内存，使 HTTPS 证书证明等大规模应用可行（大网站每秒发行数百万个证明需要 PB 级 RAM 如果每个证明 2 GB）

## 我的笔记
- 这是目前读到的最清醒、最诚实的 zkVM 行业评估之一。a16z 作为加密领域最大 VC，其研究合伙人发布这样一份审慎的时间线预测（2年/4年+/多年）值得高度重视——尤其当市场上大量项目声称"主网上线、生产就绪"时。
- Thaler 对行业宣传的批评一针见血："1000× faster than predecessor" 的叙事被准确拆解为 "more a statement of how bad things were than how good things are"，这种框架对评估任何新兴技术都适用。
- 预编译作为"拐杖"的论点虽然有力，但略偏极端。现实中，以太坊生态中的大量计算确实由哈希和签名操作主导，预编译在短期内可能是务实的选择。Thaler 自己也承认 Stage 3 需要自动合成且形式化验证的预编译——说明预编译本身不是问题，问题在于手工编写且未形式化验证。
- 安全与性能相互依存的观点是关键洞察：当前行业存在大量"先跑起来再修安全"的心态，但 ZK 证明系统的特殊性在于安全漏洞可能完全瓦解性能分析的前提。
