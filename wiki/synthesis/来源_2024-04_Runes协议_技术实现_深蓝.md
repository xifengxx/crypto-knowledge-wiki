# Runes 协议技术实现详解：从数据结构到链上编码的完整拆解

## 阅读证据
- 总行数: 361
- Q1 (前25%): Etching 蚀刻结构包含 6 个字段——`divisibility`（小数位数，相当于 ERC20 的 decimal）、`premine`（预挖数量）、`rune`（名称，基数-26 编码）、`spacers`（名称字符间隔符）、`symbol`（货币符号，1 个 UTF8 字符）、`terms`（铸造条款，含 Amount/Cap/Height/Offset）。符文总量 = 预挖 + Amount × Cap，数量采用 uint128（非 ETH 的 uint256 也非 BTC 的 uint64）
- Q3 (中后25%): Mint 铸造已定义符文时使用 RuneId（格式 `区块高度:揭示交易索引值`，如 "2609649:946"）标识目标符文，通过一笔普通转账交易的 OP_RETURN 即可上链（无需 P2TR 两笔交易，与 Etching 不同）。系统预定义符文 UNCOMMON•GOODS 的 ID 为 1:0，每个交易可挖出一个
- Q4 (最后25%): Cenotaph 墓碑触发条件共 5 类——包含无法识别的偶数标签（Even Tags）、无法识别的标志（Flags）、Edict 输出编号大于交易实际输出数、符文 ID 的 block=0 但 tx_index≠0、Runestones 解码数据被截断。触发后输入符文被永久销毁，蚀刻操作不当则符文供应量为零且不可铸造

## 核心要点
1. **Runes 协议的完整技术栈可归纳为四大数据结构 + 三种上链机制**：Etching（创建）+ Edict（转移）+ Runestone（消息载体）+ Cenotaph（错误处理），通过 OP_RETURN + TapScript + P2TR 三种比特币原生机制实现链上操作
2. **Etching 采用 Commit-Reveal 两阶段交易且必须间隔 6 个区块以上**：第一笔 Commit 交易向 P2TR 地址转 BTC（不揭示符文名称），等待 ≥6 个区块确认后，第二笔 Reveal 交易才在 OP_RETURN 中公开蚀刻详情和 TapScript 中的名称承诺。6 区块间隔是硬性要求，为防止矿工抢跑（Front-running）
3. **符文命名使用基数-26 编码 + 渐进式解锁**：字母 A-Z 对应数值 0-25，多字母名称是累积编码（如 AA=26, AB=27），名称 "AAAAAAAAAAAAAAAAAAA" 及更长为协议保留。从区块 840,000 起，名称长度随区块高度逐步解锁，且蚀刻时必须通过 TapScript 提交对名称的 Commitment 承诺来防止抢注
4. **Edict 法令的 Delta 编码和排序规则**：多个 Edict 必须按符文 ID 排序后进行 Delta 编码以压缩交易大小。特殊规则——amount=0 表示分配该符文所有剩余单位，output=交易输出总数表示等量分配到每个非 OP_RETURN 输出
5. **符文转移遵循比特币 UTXO 模型，无需专门的转账结构**：一个 Mint 交易铸造的符文占据某个 UTXO（例如 1000 聪），直接花费该 UTXO 转账给用户 B（不包含 OP_RETURN），用户 B 即收到该符文。只有当需要复杂的多符文分配时才使用 Edict + OP_RETURN
6. **作者基于对协议的理解，指出"很多项目对符文的用法是不对的"**，并开源了 Go 语言实现的 Runestone 库（github.com/bxelab/runestone），强调 P2TR 两笔交易的 6 区块间隔是硬性要求

## 关键数据
- Etching 字段数：6 个（divisibility / premine / rune / spacers / symbol / terms），其中 Terms 又含 4 个子字段（Amount / Cap / Height[2] / Offset[2]）
- Commit-Reveal 最小间隔：6 个区块
- RuneId 编码格式：`区块高度:揭示交易索引值`，示例 "2609649:946"
- 系统符文 UNCOMMON•GOODS 的 RuneId：1:0（即区块 1 的第 0 笔交易），每笔交易可铸造一个
- 符文数量类型：uint128（最大值约 3.4×10³⁸），而非 ERC20 常用的 uint256
- Cenotaph 触发条件：5 类（不可识别偶数标签 / 不可识别标志 / Edict output 溢出 / 无效符文 ID / 数据截断）
- 名称编码：基数-26，A=0..Z=25，保留名称最小长度为 "AAAAAAAAAAAAAAAAAAA"（19 个 A）
- OP_RETURN 嵌入选入 MAGIC_NUMBER：OP_13

## 我的笔记
这篇文章的独特价值在于它是一个"协议实现者"而不是"协议使用者"的视角。作者用 Go 语言自己实现了一遍 Runes 协议后才写的这篇文章，这意味着他遇到了协议规范中那些容易被忽略的边界条件（如 Cenotaph 的 5 种触发条件、Delta 编码的正确排序方式、Commit-Reveal 的 6 区块硬性要求）。这比只读白皮书的人写的科普文章要硬核得多。

一个值得注意的矛盾：作者声称"很多项目对符文的用法是不对的"，但并未具体指出是哪些项目或哪些错误。这可能是因为当时 Runes 生态刚起步，各种钱包和交易平台的实现质量参差不齐——这本身就是 Runes 作为 UTXO 原生协议的一个隐性成本：它比 ERC-20 的 transfer() 调用复杂得多，需要开发者理解比特币脚本、Taproot、OP_RETURN 编码等底层机制，门槛远高于以太坊生态。

作者在文章末尾推广自己的 BxE 协议（基于改进版 Ordinals、让比特币 L1 支持 EVM 图灵完备智能合约），这暗示他的深层动机可能不只是"技术科普"，而是为 BxE 协议中接入 Runes 做铺垫。BxE 的主张——"在比特币一层网络实现，无需搭建二层网络"——与当前 BTC L2 的主流叙事形成对比，值得后续追踪其实际进展。
